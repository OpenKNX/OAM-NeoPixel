# Hardware selection, ports and board tables

The ETS hardware selection, the per-board port lists and the board tables of OAM-NeoPixel are generated by the
generic generator of OGM-HardwareConfig. Reference: `lib/OGM-HardwareConfig/generator/README.md`.

## Inputs

| File | Content |
|---|---|
| `lib/OGM-HardwareConfig/include/HardwareConfig/**/*.h` | per board `DEVICE_HW_ID`, `DEVICE_NAME`, ports `HW_PORT_COUNT` / `HW_PORT_<n>_GPIO` / `HW_PORT_<n>_LABEL`, hard-wired relays `HW_RELAY_COUNT` / `HW_RELAY_<n>_GPIO` / `HW_RELAY_<n>_LABEL` (onboard relays: QuinLED Dig2Go IO12, Gledopto GL-C-017WL IO18, GL-C-620WL IO18), `DEVICE_THIRD_PARTY`, `HW_LEVELSHIFTER` |
| `platformio.custom.ini` | the `release_*` / `debug_*` envs with the board define and build flags (`NEOPIXEL_DISABLE_2D`); the level shifter comes from `HW_LEVELSHIFTER` of the board header |
| `HardwareManifest.xml` | manifest: boards = every `release_*` env; hardware module (prefix `NEOHW`, ModuleType 45); Network (`KNX_IP_LAN`/`KNX_IP_WIFI` in some env: third-party boards and KNeoPix S3 V1/V1.5), No2D (env flag), Wifi (`KNX_IP_WIFI` in any env of the board: the NETW selection and WiFi page are wrapped in `%NEOHW_CAP_Wifi_OR_NONE%`), ThirdParty (`DEVICE_THIRD_PARTY`), Relays (`<Value expr="HW_RELAY_COUNT" query="false">`, `<Set>` for KNeoPix 4, UP1 1, QuinLED Uno/Quad (V3, V4), Octa (V1, V2, V4) and Next2 1, Gledopto 309WL 1, 017WL 2, ETS only); `<Ports board="*" excludeRelayPins="true">`; the `<Generate>` list |
| `HardwareManifest.slots` | board number per HW-ID (part of the parameter IDs `...HW<n>`); committed, never renumbered |
| `src/hw/*.xml` | NeoPixel templates: port types, relay types, share blocks, strip blocks |
| `src/NeoPixel.script.src.js` | ETS script source; `@@use` lines expand to the board tables (port labels, port GPIOs, board numbers, network list), the effect blocks are filled by `Build-EffectParameters.ps1` |

An output is only written when its content changes.

## Running it

- `scripts/Build-Release.ps1` runs `Build-EffectParameters.ps1`, then `Normalize-LineEndings.ps1`, then the shared
  OGM-Common preprocess, which runs the generator and the producer.
- Alone (VS Code task "Build HardwareConfig"): `pwsh lib/OGM-HardwareConfig/generator/Build-HardwareProfile.ps1`
  in the repository root; it yields a current `src/NeoPixel.script.js` from `src/NeoPixel.script.src.js`.

## Values the ETS stores

- Hardware selection (`NEOHW_HardwareSelect`, `UP-4500001`, module NEOHW): the `DEVICE_HW_ID`, 0 = not selected.
- Port selection: hardware port number - 1 (`HW_PORT_<n>` -> value n-1), 10 = manual GPIO, 15 = not selected.
  All boards' port parameters of one strip signal (data `%TT%0%C%900+n`, clock `950+n`) and of one relay (`200 + 50 (r-1) + n`)
  share one byte; the firmware reads it through a carrier parameter (`NEO<n>DataPort`, `NEO<n>ClockPort`,
  `NEOExternalRelay<r>Port`) and maps value k to `HW_PORT_<k+1>_GPIO` of its own board header (`hwPortGpio`,
  OGM-HardwareConfig `include/HardwareConfig/Helpers/HardwarePorts.h`).
- Limit: value 10 = manual GPIO, so NeoPixel stores hardware ports 1..10 per board (`<Ports max="10">` in the manifest stops
  the generator, `src/HardwareMappingLogic.h` stops the build for a board with more ports; OGM-HardwareConfig itself reads up
  to 64). A board with more ports (e.g. ESP32-P4) needs another value layout - changing it breaks stored values (open point).
- The firmware uses a port byte only while the selection equals its own `DEVICE_HW_ID`; with no or another board
  selected every strip and relay stays off (ETS writes the byte only from the selected board's parameter).

## Hard-wired relays

Only an onboard relay is hard-wired (`HW_RELAY_COUNT`): QuinLED Dig2Go IO12, Gledopto GL-C-017WL IO18 and GL-C-620WL IO18.
Relay n <= `HW_RELAY_COUNT` has no relay port parameter, its page shows "Anschluss: <HW_RELAY_n_LABEL>"; every further
relay keeps its port parameter (017WL: relay 1 = IO18, relay 2 on a port; Relays value 2). The onboard relay pin is not
offered as LED port (a hole: the other ports keep their numbers); the relay count shows an error above the Relays value.
The firmware takes relay n <= `HW_RELAY_COUNT` from `HW_RELAY_<n>_GPIO` (port byte ignored) and every further relay from its
port byte (`HardwareProfile::relaySignalGpio`); it refuses a strip whose port value or manual GPIO is an onboard relay pin,
whatever the relay count, and the ETS conflict check flags such a GPIO at the strip, also with relay count 0 (the relay
page, shown for relay n while the relay count is at least n, shows it there too). The relay output of QuinLED Uno, Quad, Octa, Next2 and the I/O ports of
Gledopto 309WL (IO12) and 017WL (IO13) are normal ports: LED or relay, as in 2.0.

## Network and WiFi modules

The network module is switched by the OpenKNX module checkbox „Netzwerk" (`BASE_ModuleEnabled_NET`, page OpenKNX →
„Module"). `<Fix name="NetOff" capability="!Network" value="0" show="assign">` of `HardwareManifest.xml` switches it off on
the boards without capability Network (`KNX_IP_LAN` or `KNX_IP_WIFI` in some env of the board) (block `Fix_NetOff` in the
hardware page of both product XMLs). On the boards with Network and while nothing is selected (state after "Aktualisieren")
no Assign is active and the checkbox has its own value (default on), so a download keeps the network settings. After leaving
a board without Network the Assign no longer applies and the checkbox has its own value again (ETS6, measured with the demo
module: it comes back); a value an earlier Dev version wrote by script (off) stays. Off hides the
Netzwerk channel.

Firmware (`src/main.cpp`): an IP build (`MASK_VERSION 0x57B0`) always adds the network module. A TP build with
`KNX_IP_LAN`/`KNX_IP_WIFI` adds it when the device is unprogrammed or the checkbox is on, and logs "network module not
started" otherwise; KNX stays on TP. A firmware without the network module reports NET and NETW as unsupported
(`openknx.unsupportedEtsModule`, function property 158/2), a LAN-only firmware NETW. The buttons „Nicht unterstützte
Module deaktivieren" / „Komplettabgleich aller Module" (OpenKNX → „Module", shown by `%BASE_ShowSyncModulesButton%` = 1
in `src/NeoPixel.conf.xml`) then switch the checkbox off.

NETW has no checkbox row (the producer lists none for it, as in OAM-IP-Interface): ETS never writes its bit (an
inactive union member writes nothing, the bit stays 0), so the firmware does not read `ParamBASE_ModuleEnabled_NETW`.
The WiFi settings follow the capability Wifi (`%NEOHW_CAP_Wifi_OR_NONE%`).

| Boards | „Netzwerk" after the selection | firmware |
|---|---|---|
| third-party (every env KNX over IP) | on | IP build: network always on |
| KNeoPix ESP32 S3 V1/V1.5 (TP, TP+WiFi, IP envs) | on | TP: no network module (reports NET/NETW, the sync button switches the checkbox off); TP+WiFi: checkbox switches the network; IP: always on |
| other boards (incl. KNeoPix ESP32 C3/C5/C6: no env has the network module) | off | no network module (reports NET/NETW) |

The developer view shows per board „Netzwerk" / „WLAN": ja, nein, „je nach Firmware-Variante" or „ja (immer ein, KNX
über IP)" on boards whose every env runs KNX over IP.

## Device query

The button of the hardware module calls function property 158/4; the firmware answers status, `DEVICE_HW_ID` and the
capability bits from `include/HardwareProfileData.h` (Relays is ETS only and not part of the answer). ETS sets the
selection and reports a capability that differs from the expected profile. 158/10 is the Studio readback only.

## Port conflicts

The generator's check (`HardwareManifest.xml <Conflicts>`, OGM-HardwareConfig README "GPIO-Konflikte"): one calculation
(`PC-%TT%00900`, `NEOHW_conflictCheck` in `NeoPixel.hw.module.gen.js`) resolves every active signal to a GPIO of the selected
board and flags two signals on one GPIO. Signals: data and clock of strips 1..NumberOfLEDStrips (per-board port parameter of
the selected board; "Manuell" = `SPIMOSIGPIO` for the SPI LED types 5 6 21 22 23 24 25, else `DataGPIO`; clock only for
those types),
relays 1..RelayCount (per-board port, "Manuell" = `NEOExternalRelay<r>GPIO`), hard-wired relays always (`HW_RELAY_<n>_GPIO`).
No board selected: no check. Flags without memory: relays `P-%TT%00900..00903`, strip n data `P-%TT%0091n`, clock
`P-%TT%0092n`; the strip page includes `ConflictChannel_StripData` / `StripClock` (named through `%C%`), the relay pages
`Conflict_Relay<n>`. Port values: `portManualValue="10"` / `portNoneValue="15"`, also read by the firmware
(`HardwareProfile::signalGpio`, `relaySignalGpio`). Known limits: the clock of an SPI strip counts while its data port is
"not selected" (the firmware leaves that strip off and claims no pin), and a strip with 0 LEDs is checked (the firmware skips it).

## Board table EffectsOff (effects per board)

`HardwareManifest.xml` holds `<BoardTable name="EffectsOff" header="src/NeoPixelEffectGroups.h" scan="^NEO_FXOFF_(\d+)$" />`
(OGM-HardwareConfig README "Board-Tabellen"). Per `release_*` env the generator runs the preprocessor over
`src/NeoPixelEffectGroups.h` with the `-D` flags of the env (no `build_unflags`, no `-include`) and reads every
`NEO_FXOFF_<n>` (1 = effect number n is left out of that firmware, same conditions as `EffectPool::getEffectByIndex()`).
The ETS script gets one row per HW-ID: `var NEOHW_table_EffectsOff = { <HW-ID>: { any: [...], all: [...] } }`, index =
effect number; `any` = bitwise OR over the envs of the board (some firmware leaves the effect out), `all` = bitwise AND
(every firmware leaves it out).

`<ValueNotices>` turns the table into XML (`src/NeoPixel.hw.notices.gen.xml`, no script): per effect selector a block
`ValueNotice_SegmentFx` (segment template), `ValueNotice_SceneFx` (part Scene), `ValueNotice_CueFx` (part Cue) with a
choose on the hardware selection, one when per group of boards with the same values, inside a choose on the effect value:
error "Effekt nicht verfügbar" for the numbers in `all`, hint for the numbers only in `any`; no board selected or an effect
the board has: no notice. It reads the effect selector only: on boards with the capability No2D the visible list without
the 2D effects (`<Filters>`, below) copies its value into it. The header comes from `scripts/Build-EffectParameters.ps1` (groups in
`src/NeoPixel.EffectGroups.xml`, see `doc/Effect-Flags.md`), so that script runs before the hardware generator
(`Build-Release.ps1` keeps this order).

## Adding a board

1. Header block in OGM-HardwareConfig with `DEVICE_HW_ID`, `DEVICE_NAME` and the `HW_PORT_*` lines (no gaps).
2. A `release_<board>` env in `platformio.custom.ini` (board, board define, product flags) and its `debug_` twin in
   `platformio.custom.dev.ini`; relays offered in ETS: a `<Set>` line in `HardwareManifest.xml` if the default 0 does not fit.
3. Run the generator: the board gets the next free number in `HardwareManifest.slots` (commit it).
4. Raise the ApplicationVersion (the ETS content changed).
